## الواجهة: دَرْب السيرة
الواجهة (React + Vite) متصلة بالباك عبر `/api` (البروكسي في `vite.config.js`):

| الواجهة | الـendpoint |
|---|---|
| خريطة الفصول (٣٤ فصل) | `GET /api/chapters` |
| قراءة الفصل: الأحداث، المقدمة، الدروس، اختبار الفصل، وموقع كل حدث `geo` | `GET /api/chapters/{id}` |
| تحقق من فهمي (تلخيص القارئ) | `POST /api/check` |
| دردشة دَالّ (من الرئيسية أو من الفصل أو من الحدث) | `POST /api/chat` |

- كل شاشة تظهر حسب توفر بياناتها: «دروس وعبر» لو الفصل فيه دروس، «اختبار الفصل» لو فيه أسئلة، «اختبر فهم هذا الحدث» لو نص الحدث ≤ 5500 حرف، والتبديل بين الصياغة القصصية والنص الأصلي لو الحدث له `story`.
- **أين نحن الآن على الخريطة**: الباك بيقرأ `location_name` و`geo_coordinates` من `data/raheeq_events_with_sources.csv` ويرجّعهم في `event.geo = {lat, lng, name, basis}`. الزر بيفتح Google Maps على موقع الحدث الحالي، ولو الحدث مالوش موقع بيستخدم آخر موقع معروف قبله في الفصل (أو أقرب موقع بعده).
- التقدم والـstreak ونتائج التحقق ومظهر القراءة (فاتح/سيبيا/داكن وحجم الخط) بتتخزن في `localStorage` تحت `darb:v1` (بدون تسجيل دخول).
- الخط: `Elgharib` للواجهة، و`IBM Plex Sans Arabic` لنصوص القراءة الطويلة (المتغير `--font-read` في `styles.css`). اللوجو في `frontend/src/assets/logo.png`.
- محتاجة `GROQ_API_KEY` في `.env` للتحقق والدردشة (الباك بيقراه).

## السرد الصوتي (TTS)

كل حدث في كل فصل فيه زر **«استمع إلى الحدث»**: الراوي يقرأ عنوان الحدث ونصه، والجملة المسموعة تظهر تحت الزر، والآيات القرآنية لا يقرؤها الذكاء الاصطناعي بل تُشغَّل **تلاوة حقيقية** (الشيخ مشاري العفاسي من EveryAyah) في موضعها.

### للتجربة (المحكّمين): لا يحتاج GPU ولا أي خطوة إضافية
الصوت **مولَّد مسبقًا** ومحفوظ في `data/audio/` (لكل حدث `<id>.mp3` + `<id>.json` فيه توقيت كل جملة ومواضع الآيات). الباك يقدّمه على `/api/audio/…`، فيكفي تشغيل الباك والفرونت كالمعتاد (الخطوتان 3 و4 أعلاه).
- تشغيل التلاوات يحتاج اتصالًا بالإنترنت؛ بدونه يُعرض نص الآية ويكمل السرد.
- لو حدث ليس له ملف صوت، الزر لا يظهر له.

### إعادة توليد الصوت (لفريق التطوير فقط)
محرك الصوت في مجلد `tts/` (XTTS-v2 + معالجة النص العربي + ربط الآيات بالتلاوات). التوليد يحتاج GPU (Kaggle)، باستخدام `tts/notebooks/pregenerate_kaggle.ipynb` (التفاصيل في `tts/README.md`).

### (اختياري) السرد المباشر
لو خادم الصوت شغال (`tts/`، مثلًا على Kaggle مع نفق)، ضعي عنوانه في `frontend/.env.local`:
`VITE_TTS_WS_URL=wss://<…>.trycloudflare.com/ws/tts` — فيُستخدم للأحداث التي ليس لها صوت جاهز.

## المساعد الذكي «دَالّ» (RAG)

الشات يجيب من **مصادر السيرة المفهرسة** مع ذكر المصدر:
- **بحث هجين:** متجهات دلالية (`BAAI/bge-m3`) + بحث بالكلمات (BM25) في **Qdrant**، مدموجة بـ RRF.
- **الامتناع عند عدم الثقة:** لو لم يتجاوز أي مصدر حد التشابه (`DENSE_THRESHOLD`) لا يخمّن.
- **توليد مقيّد بالمصادر:** Gemini يجيب من النصوص المسترجعة فقط، مع أرقام الاستشهاد `[1]` وتظهر المصادر أسفل الإجابة.
- يعرف الحدث أو الفصل الذي يقرؤه المستخدم، فسؤال مثل «لخّص لي هذا الحدث» يبحث عن الحدث الصحيح.
- لو السؤال غير موجود في المصادر، أو خدمة RAG غير مفعّلة، يجيب المساعد الأساسي من نص الحدث المعروض فقط.

### تفعيله
1. `pip install -r requirements-rag.txt`
2. في `.env`: `GEMINI_API_KEY` و`QDRANT_URL` و`QDRANT_API_KEY` و`HF_TOKEN` (انظر `.env.example`).
3. شغّلي الباك كالمعتاد؛ يطبع `chat engine: RAG (Qdrant + Gemini)` ثم `RAG ready (embeddings: api)`.

**أين يُحسب تمثيل السؤال (embedding)؟** يحدده `RAG_EMBEDDINGS` في `.env`:
- `api` (الافتراضي): عبر Hugging Face Inference API لنفس النموذج `BAAI/bge-m3`، فالباك خفيف (بدون torch) ويعمل على استضافة مجانية.
- `local`: النموذج يعمل على الجهاز نفسه (`pip install -r requirements-rag-local.txt`، حوالي 2 جيجابايت).
للتأكد أن الطريقتين تعطيان نفس نتائج البحث: `cd backend && python check_embeddings.py`.

## النشر (رابط واحد للموقع)
الموقع والـ API والصوت والمساعد يعملون من خدمة واحدة على **Render** (مجانية) عبر `render.yaml`:
1. ابني الواجهة وارفعيها: `cd frontend && npm run build && cd .. && git add -f -A frontend/dist`.
2. في Render: **New → Blueprint** واختاري هذا المستودع، ثم أدخلي المفاتيح المطلوبة.
3. الخدمة المجانية تنام بعد فترة بدون زيارات؛ أول فتح بعدها يأخذ حوالي دقيقة.
